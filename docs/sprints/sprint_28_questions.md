🟪 SPRINT 28 — FINAL VALIDATION PACK (Architecture Knowledge Base & System Context Layer)

⸻

🎯 Ціль перевірки

Підтвердити, що:
	•	архітектура має єдине джерело правди
	•	документація:
	•	актуальна
	•	зв’язана з кодом
	•	використовується
	•	рішення не губляться
	•	LLM/агенти можуть реально використовувати цей контекст

🟫 SECTION 1 — Architecture Source of Truth

⸻

1.1 Чи існує єдиний AKB (Architecture Knowledge Base)?
	•	є одна точка входу (repo/директорія)
	•	немає розкиданих doc-файлів по всьому проекту
	•	зрозуміло “де дивитися архітектуру”

⸻

1.2 Чи AKB є реально source of truth?

Перевірити:
	•	команда користується ним
	•	рішення не приймаються “поза системою”
	•	немає паралельних джерел правди

⸻

1.3 Чи AKB version-controlled?
	•	всі зміни проходять через PR
	•	є історія змін
	•	можна подивитись “як було раніше”

⸻

🟫 SECTION 2 — C4 Model (Reality vs Diagram)

⸻

2.1 Чи існує Context Diagram?
	•	система описана як єдине ціле
	•	є external actors
	•	boundaries визначені

⸻

2.2 Чи існує Container Diagram?
	•	всі ключові сервіси присутні:
	•	control plane
	•	runtime
	•	workers
	•	governance
	•	telemetry
	•	storage
	•	UI

⸻

2.3 Чи діаграми відповідають реальності?

❗ КРИТИЧНО

Сценарій:
	•	взяти 2–3 сервіси з коду

Очікування:
	•	вони є на діаграмі
	•	взаємодії не вигадані
	•	немає “фантазійної архітектури”

⸻

2.4 Чи діаграми генеруються, а не малюються вручну?
	•	є DSL або reproducible генерація
	•	немає “PNG без source”
	•	можна змінити модель → отримати нову діаграму

⸻

🟫 SECTION 3 — arc42 Documentation

⸻

3.1 Чи структура arc42 повна?
	•	introduction
	•	building blocks
	•	runtime view
	•	deployment view
	•	risks

⸻

3.2 Чи runtime view відповідає системі?
	•	описаний execution flow
	•	описаний multi-agent flow
	•	описаний governance
	•	описаний control plane

⸻

3.3 Чи deployment view реальний?
	•	local setup описаний
	•	docker/container описаний
	•	future cloud model описаний

⸻

3.4 Чи документація не “водяна”?
	•	конкретні компоненти
	•	конкретні зв’язки
	•	мінімум абстрактного тексту

⸻

🟫 SECTION 4 — ADR (Decision Memory)

⸻

4.1 Чи існує ADR система?
	•	є окрема папка
	•	є шаблон
	•	є naming convention

⸻

4.2 Чи ADR реально використовуються?
	•	мінімум 8–12 записів
	•	ключові рішення зафіксовані

⸻

4.3 Чи ADR відповідають реальності?

Сценарій:
	•	взяти рішення (наприклад control plane)

Очікування:
	•	реалізація відповідає ADR
	•	немає “ми зробили інакше, але не оновили ADR”

⸻

4.4 Чи ADR пояснюють “чому”?
	•	є альтернативи
	•	є аргументація
	•	є наслідки

⸻

🟫 SECTION 5 — Linking Layer (КЛЮЧОВЕ)

⸻

5.1 Code → Architecture
	•	кожен ключовий сервіс має mapping
	•	зрозуміло “цей код = цей компонент”

⸻

5.2 Architecture → Code
	•	з діаграми можна знайти код
	•	немає “мертвих” компонентів

⸻

5.3 ADR → Components
	•	рішення прив’язані до компонентів
	•	компоненти знають свої ADR

⸻

❗ КРИТИЧНО
	•	немає “відірваної документації”

⸻

🟫 SECTION 6 — Agent Context Layer

⸻

6.1 Чи існує системний контекст для агентів?
	•	опис системи є
	•	опис компонентів є
	•	опис принципів є

⸻

6.2 Чи формат придатний для LLM?
	•	структурований
	•	не “есе”
	•	легко парситься

⸻

6.3 Чи агент реально використовує цей контекст?

Сценарій:
	•	дати агенту задачу

Очікування:
	•	він використовує правильні компоненти
	•	не вигадує архітектуру
	•	не конфліктує з реальною системою

⸻

🟫 SECTION 7 — Export / Visualization

⸻

7.1 Чи діаграми доступні локально?
	•	можна відкрити без SaaS
	•	HTML / PNG / SVG доступні

⸻

7.2 Чи документація читається як портал?
	•	є навігація
	•	є структура
	•	можна швидко знайти потрібне

⸻

7.3 Чи це реально використовують?
	•	dev відкриває docs
	•	не “лежить мертвим грузом”

⸻

🟫 SECTION 8 — Workflow Integration

⸻

8.1 Чи ADR інтегрований у процес?
	•	великі зміни → ADR
	•	ADR review існує

⸻

8.2 Чи doc sync enforced?
	•	code change → doc update
	•	перевірка в PR

⸻

8.3 Чи є anti-drift механізм?
	•	docs не відстають від коду
	•	є регулярний audit

⸻

🟫 SECTION 9 — Consistency Audit

⸻

9.1 Чи docs = code?
	•	компоненти співпадають
	•	flows співпадають

⸻

9.2 Чи немає “мертвих знань”?
	•	немає описаних, але не існуючих сервісів
	•	немає реалізованих, але не описаних сервісів

⸻

9.3 Чи немає дублювання?
	•	один компонент → одне місце опису
	•	немає суперечностей

⸻

🟫 SECTION 10 — Agent Comprehension Test

⸻

10.1 Сценарій: пояснення системи

Запитати агента:

“як працює система?”

Очікування:
	•	відповідає реальності
	•	не вигадує

⸻

10.2 Сценарій: знайти компонент

“де реалізований control plane?”

	•	агент показує правильне місце

⸻

10.3 Сценарій: запропонувати зміну

“як додати новий сервіс?”

	•	відповідає архітектурі
	•	не ламає модель
